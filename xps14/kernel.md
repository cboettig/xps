# Kernel choice and the camera

Ubuntu ships two kernel flavours on this machine: the Dell/OEM `6.17.0-*-oem`
(`linux-oem-24.04d`) and the generic HWE series `7.0.0-*-generic`
(`linux-generic-hwe-24.04`). Both metapackages are marked manually installed, so both stay
updated.

**Status as of 2026-09-05.** The camera works on the generic kernel — but *not on every*
generic kernel. Current known-good set:

| Kernel | Camera | Notes |
|---|---|---|
| `6.17.0-1032-oem` | works | vendor default; kept as fallback |
| `7.0.0-30-generic` | works | **current default**, held (see below) |
| `7.0.0-31-generic` | **broken** | psys never probes; also oopses on driver unbind |

The history here matters, because this file has been wrong twice:

- An early revision assumed the OEM kernel was the only option. Wrong — see
  [What the generic kernel needs](#what-the-generic-kernel-needs).
- A later revision concluded "generic is no longer a blocker" and recommended tracking the
  `-generic-hwe-24.04` metapackages. That advice is what put `7.0.0-31` on the machine and
  broke the camera. Tracking the newest generic kernel is exactly the wrong default here.

## The kernel is only half the story

Choosing a kernel does not free this machine from the Dell stack. The camera userspace —
`icamerasrc` linked against `libcamhal.so.0`, from `dell.archive.canonical.com` — is required
on *every* kernel, OEM or generic, because noble's `libcamera 0.2.0` has no IPU7 pipeline
handler. Conversely the OEM kernel is not a Dell package at all; `linux-oem-24.04d` ships from
`archive.ubuntu.com`. See [oem-stack.md](oem-stack.md#kernel-packages-do-not-come-from-dell).

So "kernel flavour" and "vendor dependency" are independent axes. This file is only about the
first.

## Which kernel boots

Two independent mechanisms, and it is easy to mistake one for the other.

**Flavour order.** The OEM enablement package installs a GRUB drop-in — actually a symlink
into its own data directory:

```console
$ ls -l /etc/default/grub.d/oem-flavour.cfg
lrwxrwxrwx ... -> /usr/share/oem-somerville-hypno-meta/oem-flavour.cfg
$ cat /etc/default/grub.d/oem-flavour.cfg
# This file is automatically generated by oem-somerville-hypno-meta, and changes will be overriden
GRUB_FLAVOUR_ORDER=oem
```

`/usr/lib/grub/grub-sort-version` reads `GRUB_FLAVOUR_ORDER` as a flavour priority list and
sorts matching flavours ahead of everything else **before** any version comparison, so
`6.17.0-1032-oem` beats `7.0.0-31-generic` on a passive boot. It is not a version or
`saved_entry` effect.

Do not edit `oem-flavour.cfg` — it is package-owned and gets rewritten. `grub-mkconfig`
sources `/etc/default/grub.d/*.cfg` in glob order, so a later-sorting drop-in wins:

```console
$ cat /etc/default/grub.d/zz-flavour-order.cfg
GRUB_FLAVOUR_ORDER=generic
```

**Version pin.** Flavour order cannot express *which* generic kernel, and we need `-30`
specifically, so `GRUB_DEFAULT` names the entry outright:

```sh
GRUB_DEFAULT="Advanced options for Ubuntu>Ubuntu, with Linux 7.0.0-30-generic"
```

That string must match a `menuentry` title in `/boot/grub/grub.cfg` verbatim; derive it
rather than typing it:

```sh
grep -oP "^\s*menuentry '\KUbuntu, with Linux 7\.0\.0-30-generic(?=')" /boot/grub/grub.cfg
```

The menu is left visible (`GRUB_TIMEOUT_STYLE=menu`, `GRUB_TIMEOUT=5`) so a bad default can
be overridden by hand. The stock config is `hidden`/`0`, which is why tapping <kbd>Esc</kbd>
does nothing on a factory install — there is no wait to interrupt. If you land at a bare
`grub>` prompt, type `normal`.

Two things that look like evidence but are not:

- `/boot/vmlinuz` and `/boot/initrd.img` symlink to the highest version. They are maintained
  by `linux-update-symlinks`; GRUB does not consult them.
- `grub-editenv list` is empty. No `saved_entry` pin, and none is wanted.

## Holding 7.0.0-30

The `-generic-hwe-24.04` metapackages keep pulling newer kernels. Without holds, `-30` is
eventually autoremoved and the machine silently lands on a broken camera:

```sh
sudo apt-mark hold \
  linux-image-7.0.0-30-generic \
  linux-modules-7.0.0-30-generic \
  linux-modules-ipu7-7.0.0-30-generic \
  linux-modules-ipu6-7.0.0-30-generic \
  linux-modules-vision-7.0.0-30-generic
```

Check with `apt-mark showhold`. Revisit these holds whenever a new generic kernel lands —
the point is to *test* before switching, not to freeze forever.

## The 7.0.0-31 regression

Filed upstream as **[LP #2166612](https://bugs.launchpad.net/ubuntu/+source/linux-hwe-7.0/+bug/2166612)**
against `linux-hwe-7.0` (2026-09-06). If it is fixed in `-32`, the holds below
become unnecessary.

Symptom: no `/dev/ipu7-psys0`, and `/dev/video0` yields a single placeholder frame and then
stalls.

```
intel_ipu7_isys.isys intel_ipu7.isys.40: All sensor registration completed.
bus_add_device: cannot add device 'ipu7-psys0' to unregistered bus 'intel-ipu7-psys'
intel-ipu7-psys ipu7-psys0: psys device_register failed
intel_ipu7_psys.psys intel_ipu7.psys.40: probe with driver intel_ipu7_psys.psys failed with error -22
```

The sensor half is fine — `ov08x40` enumerates in the media graph exactly as on a working
kernel. Only the processing half fails, so the HAL has no psys device.

It is the in-tree core that changed, not the out-of-tree module:

| Module | Origin | `srcversion` on `-30` | on `-31` |
|---|---|---|---|
| `intel_ipu7` | in-tree (staging) | `D1E673C7A7AD4A1A400F034` | **`121F0453F296C89ED5B8418`** |
| `intel_ipu7_isys` | in-tree (staging) | `1C08CDBA2483EEF5519768A` | unchanged |
| `intel_ipu7_psys` | `linux-modules-ipu7-*` | `32D18897D60F8FF10DA6F05` | unchanged |

So `-31`'s core update broke its ordering contract with an unchanged psys module: the aux
device is created and probed before the psys module registers its bus.

### Do not unbind the IPU7 device on 7.0.0-31

The unbind/rebind re-probe trick (below, and previously recommended here for live-USB
testing) **NULL-derefs on this kernel**:

```
BUG: kernel NULL pointer dereference, address: 0000000000000008
RIP: 0010:__raw_spin_lock_irqsave+0x27/0x80
Call Trace:
 ipu7_dma_free+0x4e/0x220        [intel_ipu7]
 isys_remove+0x52/0x110          [intel_ipu7_isys]
 ipu7_bus_del_devices+0xac/0x100 [intel_ipu7]
 ipu7_pci_remove+0xa0/0x180      [intel_ipu7]
```

The writing task dies with irqs disabled and a leaked `preempt_count`, which wedges shutdown
— a subsequent `reboot` hangs and needs <kbd>REISUB</kbd>. Nothing is damaged on disk (the
oops is in driver state, and `systemd-shutdown` still syncs), but it costs an unclean reboot.
On `-31`, reboot into a good kernel instead of trying to re-probe.

### Untested lead

`resolute` carries `linux-modules-ipu7-generic-hwe-26.04` at `7.0.0-31.31+2` — a *different
build* of the modules for the same ABI as the `7.0.0-31.31~24.04.1` we have. Whether the
`+2` respin fixes this is **not verified**. Worth checking if 26.04 is on the table anyway.

## What the generic kernel needs

OEM kernels carry out-of-tree modules under `/lib/modules/<ver>/ubuntu/`. That directory is
empty on a stock generic kernel — but Ubuntu ships the same modules for the generic flavour
as separate binary packages, ordinary archive packages in `noble-updates/main`, not DKMS and
not a source build:

```sh
sudo apt install \
  linux-modules-ipu7-generic-hwe-24.04 \
  linux-modules-ipu6-generic-hwe-24.04 \
  linux-modules-vision-generic-hwe-24.04
```

| Package | Supplies | Without it |
|---|---|---|
| `linux-modules-vision-*` | `intel_cvs` | sensor's I²C device is never created; ISYS reports no sensors |
| `linux-modules-ipu7-*` | `intel-ipu7-psys`, `ipu-acpi{,-common,-pdata}`, `ov02c10` | no `/dev/ipu7-psys0`; HAL has no processing device |
| `linux-modules-ipu6-*` | IPU6-generation equivalents | unused on this hardware; installed for parity |

`intel_cvs` is the one that actually unblocks the sensor. It is the Intel Vision Sensing
Controller and satisfies the ACPI dependency chain (CVSS, `INTC10E1`) that `OVTI08F4:00`
hangs off. It is **not** upstreamed — community guides for other distros build it from
[intel/vision-drivers](https://github.com/intel/vision-drivers) by hand. On Ubuntu it is
just a package.

The `-generic-hwe-24.04` metapackages track the newest generic kernel, which is what you
want for *availability* of matching modules and what you do **not** want for stability — see
[Holding 7.0.0-30](#holding-700-30). Keep both: the metapackages so new kernels arrive with
modules, the holds so the boot default only moves deliberately.

Already in the stock generic kernel, no action needed: `intel-ipu7`, `intel-ipu7-isys`,
`ipu-bridge`, `ov08x40`, `usbio`/`gpio-usbio`/`i2c-usbio`, `v4l2loopback`.

## Module load order

Boot logs show `int3472-discrete` racing the USBIO GPIO controller:

```
int3472-discrete INT3472:00: cannot find GPIO chip INTC10E2:00, deferring
```

`INTC10E2:00` does register eventually (as `gpiochip776`), but after int3472 has stopped
retrying. A softdep forces the ordering:

```sh
echo 'softdep intel_ipu7 pre: usbio gpio_usbio i2c_usbio intel_cvs intel_skl_int3472_discrete' \
  | sudo tee /etc/modprobe.d/ipu7-order.conf
sudo update-initramfs -u -k all
```

Use `-k all`, not a single version — the conf must be in *every* kernel's initramfs or the
camera breaks on whichever one lacks it. Verify without rebooting:

```sh
lsinitramfs /boot/initrd.img-<version> | grep ipu7-order
```

This was applied at the same time as `linux-modules-vision-*`, so **it is not proven to be
required** — the vision package alone may be sufficient. Left in place because it is
harmless and the deferral race is real. It does *not* fix the `-31` psys failure; that is a
different mechanism (bus registration, not GPIO deferral).

One warning persists even on a working system and appears to be benign here:

```
int3472-discrete INT3472:00: GPIO type 0x02 unknown; the sensor may not work
```

GPIO type 0x02 is a strobe / IR-flood LED line used for face authentication. Mainline
support is [in flight upstream](https://lwn.net/Articles/1065085/) but not in 7.0.0-30. The
main camera works regardless; only IR/Windows-Hello-style functions would be affected, and
those are not used here.

## Verifying

The camera pipeline is `icamerasrc` → `v4l2-relayd` → `v4l2loopback` (`/dev/video0`), with
`icamerasrc` sitting on `libcamhal-ipu75xa` (`75xa` = Panther Lake). Check it in this order —
each step localises the failure to one layer:

```sh
lsmod | grep -E 'intel_cvs|ipu7_psys'              # modules loaded
ls -l /dev/ipu7-psys0                              # psys device node exists
media-ctl -d /dev/media0 -p | grep ov08x40         # sensor half
ls /sys/bus/i2c/drivers/ov08x40/                   # should list i2c-OVTI08F4:00
```

A working system shows the sensor as a media entity:

```console
$ media-ctl -d /dev/media0 -p | grep ov08x40
- entity 233: ov08x40 4-0036 (1 pad, 1 link, 0 routes)
```

and the boot log reports:

```
intel-ipu7 0000:00:05.0: Found supported sensor OVTI08F4:00
intel-ipu7 0000:00:05.0: Connected 1 cameras
intel_ipu7_psys.psys intel_ipu7.psys.40: IPU psys probe done.
```

`IPU psys probe done.` is the line that separates `-30` from `-31`. Grep for it directly:

```sh
journalctl -b -k | grep -E 'IPU psys probe done|psys device_register failed'
```

Then capture actual pixels:

```sh
gst-launch-1.0 -q v4l2src device=/dev/video0 num-buffers=20 ! videoconvert ! jpegenc \
  ! multifilesink location=frame%02d.jpg
ls -l frame*.jpg | awk '{print $5}' | sort -u | wc -l    # must be > 1
```

### Three traps when testing

**`/dev/video0` always yields a frame.** It is a `v4l2loopback` node, so
`v4l2-ctl --stream-mmap` succeeds and dequeues a placeholder even when the camera is
completely dead. A successful grab there proves nothing.

**One file is not a pass.** On broken `-31`, the pipeline wrote `frame00.jpg` and then hung
until timeout. Count *distinct file sizes*, not files: 20 frames at 20 different sizes is a
pass, 20 identical sizes or a single file is not.

**Running `icamerasrc` as your user gives a misleading error.** `/dev/ipu7-psys0` is
`root:root 0600` with no udev rule granting group access, so a user-run pipeline fails at
psys configuration even on a fully working system:

```console
$ gst-launch-1.0 -q icamerasrc num-buffers=5 ! fakesink
CamHAL[ERR] ProcessingUnit: @configure configure psys dag failed:-38
```

`v4l2-relayd` runs as a root system service and is unaffected. Test through `/dev/video0`,
not by invoking `icamerasrc` directly.

### Failure signatures

| Symptom | Cause |
|---|---|
| `psys device_register failed`, probe `-22`, no `/dev/ipu7-psys0` | kernel `7.0.0-31` regression — boot `-30` |
| `CamHAL: parseSensors: No sensors available`, no `ov08x40` in media graph | `intel_cvs` (`linux-modules-vision-*`) missing |
| `modinfo: Module intel-ipu7-psys not found`, only `isys` loads | `linux-modules-ipu7-*` missing |
| `configure psys dag failed:-38` from a user shell | not a fault — psys node is root-only |
| GLib `G_IS_PARAM_SPEC` assertions from `v4l2-relayd` | `icamerasrc` failed to init; look upstream of it |

## Current versions

```console
$ uname -r
7.0.0-30-generic                    # verified working 2026-09-05
$ dpkg -l | grep -E 'linux-modules-(ipu[67]|vision)-generic-hwe'
ii  linux-modules-ipu6-generic-hwe-24.04    7.0.0-31.31~24.04.1
ii  linux-modules-ipu7-generic-hwe-24.04    7.0.0-31.31~24.04.1
ii  linux-modules-vision-generic-hwe-24.04  7.0.0-31.31~24.04.1
```

Note the metapackages sit at `-31` while the *booted* kernel is held at `-30`; the
version-pinned `7.0.0-30-generic` module packages are what actually load. Both `-30` and
`-31` module sets are installed.

The OEM kernel `6.17.0-1032-oem` remains installed and working. It is no longer the GRUB
default, but it is a second known-good fallback and should not be removed while `-31` is
broken.
