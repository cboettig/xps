# OEM kernel dependency

Ubuntu ships two kernel flavours on this machine: the Dell/OEM `6.17.0-*-oem` series
(`linux-oem-24.04d`) and the generic HWE series `7.0.0-*-generic`
(`linux-generic-hwe-24.04`). Both metapackages are marked manually installed, so both stay
updated.

**Status as of 2026-08-27: the generic kernel is no longer a blocker.** The built-in camera
works on `7.0.0-30-generic` after installing three module packages that are already in
`noble-updates/main`. This note records what was actually required, and how to tell the
failure modes apart. An earlier revision of this file assumed the OEM kernel was the only
option; that has now been tested and is wrong.

## Which kernel boots

The OEM kernel is the default, and *not* because of a version comparison. The OEM
enablement package installs a GRUB drop-in:

```console
$ cat /etc/default/grub.d/oem-flavour.cfg
# This file is automatically generated by oem-somerville-hypno-meta, and changes will be overriden
GRUB_FLAVOUR_ORDER=oem
```

`grub-mkconfig` honours `GRUB_FLAVOUR_ORDER` and sorts `*-oem` kernels ahead of every other
flavour **regardless of version number**, so `6.17.0-1032-oem` wins the default slot over
`7.0.0-30-generic`. A passive reboot always lands on OEM. No manual pinning is needed, and
the pinning options an earlier revision of this file suggested are unnecessary.

Two things that look like evidence but are not:

- `/boot/vmlinuz` and `/boot/initrd.img` symlink to the highest version (generic). They are
  maintained by `linux-update-symlinks`; GRUB does not consult them. Ignore them.
- `grub-editenv list` is empty. There is no `saved_entry` pin and none is required.

To boot generic, either use `sudo grub-reboot "Advanced options for Ubuntu>Ubuntu, with Linux
7.0.0-30-generic"` for a one-shot, or make the menu visible while testing:

```sh
sudo sed -i 's/^GRUB_TIMEOUT_STYLE=hidden/GRUB_TIMEOUT_STYLE=menu/; s/^GRUB_TIMEOUT=0/GRUB_TIMEOUT=5/' /etc/default/grub
sudo update-grub
```

`GRUB_TIMEOUT=0` + `GRUB_TIMEOUT_STYLE=hidden` is why tapping <kbd>Esc</kbd> never works —
there is no wait to interrupt. If you do land at a bare `grub>` prompt, type `normal` to get
the menu back.

## What the generic kernel needs

OEM kernels carry out-of-tree modules under `/lib/modules/<ver>/ubuntu/`. That directory is
empty on a stock generic kernel — but Ubuntu ships the same modules for the generic flavour
as separate binary packages. They are ordinary archive packages in `noble-updates/main`, not
DKMS and not a source build:

```sh
sudo apt install \
  linux-modules-ipu7-generic-hwe-24.04 \
  linux-modules-ipu6-generic-hwe-24.04 \
  linux-modules-vision-generic-hwe-24.04
```

Use the `-generic-hwe-24.04` metapackages rather than the version-pinned
`linux-modules-*-7.0.0-30-generic` names, so future kernel updates pull matching modules
instead of silently losing the camera.

| Package | Supplies | Without it |
|---|---|---|
| `linux-modules-vision-*` | `intel_cvs` | sensor's I²C device is never created; ISYS reports no sensors |
| `linux-modules-ipu7-*` | `intel-ipu7-psys`, `ipu-acpi{,-common,-pdata}`, `ov02c10` | no `/dev/ipu7-psys0`; HAL has no processing device |
| `linux-modules-ipu6-*` | IPU6-generation equivalents | unused on this hardware; installed for parity |

`intel_cvs` is the one that actually unblocks the sensor. It is the Intel Vision Sensing
Controller and satisfies the ACPI dependency chain (CVSS, `INTC10E1`) that `OVTI08F4:00`
hangs off. It is **not** upstreamed — community guides for other distros build it from
[intel/vision-drivers](https://github.com/intel/vision-drivers) by hand. On Ubuntu it is
just a package.

Already in the stock generic kernel, no action needed: `intel-ipu7`, `intel-ipu7-isys`,
`ipu-bridge`, `ov08x40`, `usbio`/`gpio-usbio`/`i2c-usbio`, `v4l2loopback`.

## Module load order

Boot logs show `int3472-discrete` racing the USBIO GPIO controller:

```
int3472-discrete INT3472:00: cannot find GPIO chip INTC10E2:00, deferring
```

`INTC10E2:00` does register eventually (as `gpiochip776`), but after int3472 has stopped
retrying. A softdep forces the ordering:

```sh
echo 'softdep intel_ipu7 pre: usbio gpio_usbio i2c_usbio intel_cvs intel_skl_int3472_discrete' \
  | sudo tee /etc/modprobe.d/ipu7-order.conf
sudo update-initramfs -u -k 7.0.0-30-generic
```

This was applied at the same time as `linux-modules-vision-*`, so **it is not proven to be
required** — the vision package alone may be sufficient. Left in place because it is
harmless and the deferral race is real.

One warning persists even on a working system and appears to be benign here:

```
int3472-discrete INT3472:00: GPIO type 0x02 unknown; the sensor may not work
```

GPIO type 0x02 is a strobe / IR-flood LED line used for face authentication. Mainline
support is [in flight upstream](https://lwn.net/Articles/1065085/) but not in 7.0.0-30. The
main camera works regardless; only IR/Windows-Hello-style functions would be affected, and
those are not used here.

## Verifying

The camera pipeline is `icamerasrc` → `v4l2-relayd` → `v4l2loopback` (`/dev/video0`), with
`icamerasrc` sitting on `libcamhal-ipu75xa` (`75xa` = Panther Lake). Check it in this order —
each step localises the failure to one layer:

```sh
lsmod | grep -E 'intel_cvs|ipu7_psys'              # modules loaded
ls -l /dev/ipu7-psys0                              # psys device node exists
media-ctl -d /dev/media0 -p | grep ov08x40         # THE decisive check
ls /sys/bus/i2c/drivers/ov08x40/                   # should list i2c-OVTI08F4:00
```

A working system shows the sensor as a media entity:

```console
$ media-ctl -d /dev/media0 -p | grep ov08x40
- entity 233: ov08x40 4-0036 (1 pad, 1 link, 0 routes)
```

and the boot log reports:

```
intel-ipu7 0000:00:05.0: Found supported sensor OVTI08F4:00
intel-ipu7 0000:00:05.0: Connected 1 cameras
intel_ipu7_psys.psys intel_ipu7.psys.40: IPU psys probe done.
```

Then capture actual pixels:

```sh
gst-launch-1.0 -q v4l2src device=/dev/video0 num-buffers=15 ! videoconvert ! jpegenc \
  ! multifilesink location=frame%02d.jpg
```

### Two traps when testing

**`/dev/video0` always yields a frame.** It is a `v4l2loopback` node, so
`v4l2-ctl --stream-mmap` succeeds and dequeues a placeholder even when the camera is
completely dead. A successful grab there proves nothing. Look at the JPEGs, or check that
their sizes vary between frames.

**Running `icamerasrc` as your user gives a misleading error.** `/dev/ipu7-psys0` is
`root:root 0600` with no udev rule granting group access, so a user-run pipeline fails at
psys configuration even on a fully working system:

```console
$ gst-launch-1.0 -q icamerasrc num-buffers=5 ! fakesink
CamHAL[ERR] ProcessingUnit: @configure configure psys dag failed:-38
```

`v4l2-relayd` runs as a root system service and is unaffected. Test through `/dev/video0`,
not by invoking `icamerasrc` directly.

### Failure signatures

| Symptom | Missing piece |
|---|---|
| `CamHAL: parseSensors: No sensors available`, no `ov08x40` in media graph | `intel_cvs` (`linux-modules-vision-*`) |
| `modinfo: Module intel-ipu7-psys not found`, only `isys` loads | `linux-modules-ipu7-*` |
| `configure psys dag failed:-38` from a user shell | not a fault — psys node is root-only |
| GLib `G_IS_PARAM_SPEC` assertions from `v4l2-relayd` | `icamerasrc` failed to init; look upstream of it |

## Bearing on Ubuntu 26.04

The camera was the reason this machine was pinned to the OEM kernel, and that reason is now
gone — but 26.04 is a separate question, because it changes the *userspace* stack rather
than the kernel one.

- Kernel side looks fine. `linux-modules-vision-generic-hwe-26.04` exists at the same
  `7.0.0-30` version, so the module packaging carries forward.
- Userspace changes completely. `libcamhal*` and `gstreamer1.0-icamera` are **absent from
  resolute**; 26.04 ships libcamera 0.7.0, which has a native `intel-ipu7` pipeline handler.
  So the `icamerasrc` → `v4l2-relayd` path documented in [camera.md](camera.md) — including
  the `flip-mode=vhflip` rotation fix — does not carry over unchanged.

### Testing 26.04 from a live USB

The `26.04.1` desktop ISO ships `linux-image-7.0.0-30-generic` — **the same kernel this
machine already runs** — so the packages above apply verbatim. But the ISO does *not*
include `linux-modules-{vision,ipu7,ipu6}-*`, so the camera will not work in a stock live
session. Add them by hand (~300 KB, fine in the RAM overlay):

```sh
sudo apt update
sudo apt install linux-modules-vision-7.0.0-30-generic linux-modules-ipu7-7.0.0-30-generic
```

Use the version-pinned names rather than the `-hwe-26.04` metapackages in a throwaway
session. You cannot reboot for a cold probe, so force a re-probe instead:

```sh
sudo modprobe intel_cvs
echo 0000:00:05.0 | sudo tee /sys/bus/pci/drivers/intel-ipu7/unbind
echo 0000:00:05.0 | sudo tee /sys/bus/pci/drivers/intel-ipu7/bind
media-ctl -d /dev/media0 -p | grep ov08x40      # kernel half answered
```

Then test the new userspace — `icamerasrc` does not exist on 26.04:

```sh
gst-launch-1.0 libcamerasrc num-buffers=15 ! videoconvert ! jpegenc ! multifilesink location=/tmp/f%02d.jpg
```

That answers whether libcamera 0.7.0's native `intel-ipu7` pipeline handler drives this
sensor, and the JPEGs settle whether any rotation fix is still needed. If the unbind/rebind
does not take — the ACPI-time sensor attach may not retrofit — use a persistent live USB so
a real reboot is possible.

What the ISO does carry: `libcamera0.7`, `gstreamer1.0-libcamera`, `libspa-0.2-libcamera`
(PipeWire). No `libcamhal*`, no `gstreamer1.0-icamera`.

Not a "no go", but not a free upgrade either: the whole camera userspace would need
re-verifying, and the 180° rotation fix would need a libcamera-side equivalent. Test from a
live USB before committing. Note also that sway 1.9 / kanshi 1.5.1 constraints are tracked
separately and are unrelated to this.
